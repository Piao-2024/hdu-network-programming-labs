状态：已授权实现，2026-10-29。用户已确认采用方案 A，规则版本 A1；当前已实现四模块和标准库测试。原始环境表为开发前检查快照。本文是需求及待确认事项的唯一登记处；规则以 [game-rules.md](game-rules.md) 为准，线协议以 [protocol.md](protocol.md) 为准。

## 1. 背景与范围

RemoteBet 是基于 TCP 的远程骰宝命令行游戏。第一阶段客户端和服务端在同一台 Mac 上运行，通过 `127.0.0.1:5000` 连接，端口可配置。客户端展示庄家提示、预叫、下注格式、骰子 ASCII 图案、点型及本盘输赢；服务端权威管理预叫、实际骰子、判型、结算和单盘状态。

后续用户要求支持Windows服务端与Mac客户端在局域网连接：客户端无host参数启动时提供IP:端口输入；非法地址重新输入、空输入沿用本机默认值、quit或输入中断取消。原显式host/--port兼容。服务端使用已有host绑定参数；默认仍为回环地址，需用户显式选择局域网监听。跨机器Windows实际联调尚未执行，不改变单活动客户端和A1规则。

不涉及真实资金、支付、数据库、账号、GUI、HTTP、WebSocket、持久化、断线恢复或复杂并发。不得把一次手动成功视为完整验收。

## 3. 功能需求

| 编号 | 要求 | 可测试的验收结果 |
|---|---|---|
| F01 | TCP 连接、欢迎、开盘 | 连接后依次收到 welcome、round_open；首次输入前可见预叫和六种玩法提示 |
| F02 | 统一下注命令 | 服务端接收并校验 `ya <玩法代码> <下注数量> <coin\|silver\|gold>`；合法命令只产生一盘结果 |
| F03 | 服务端权威 | 客户端请求不含实际骰子、中奖或金额字段；篡改额外字段被拒绝 |
| F04 | 六玩法 | 六种条件及优先级按规则文档测试；未确认项不能宣称验收通过 |
| F05 | 结果呈现 | 客户端用服务端结果绘制两枚骰子 ASCII 图，展示原始点数、最终点型、所选玩法输赢、净变化和币种 |
| F06 | 多盘及退出 | 结果后收到新开盘；可再下注或输入 quit；退出收到 bye 并释放连接 |
| F07 | 配置 | 默认回环地址、端口 5000；双方支持端口参数，服务端支持 host，非法端口启动前拒绝 |
| F08 | 错误可恢复 | 无效命令、过期盘号等返回明确错误，不掷骰、不结算、不改变当前预叫 |

## 4. 非功能需求

- TCP 使用标准库 `socket`；所有网络消息统一 UTF-8 JSON Lines，见协议文档；终端文字不直接作为裸 TCP 消息发送。
- 最小实现为同步阻塞、单活动客户端、串行每盘一注；不引入线程池、异步框架或通用依赖注入容器。
- 结果、整数运算及错误路径可确定性测试。规则计算与随机抽样分开，避免靠随机碰巧覆盖案例。
- 消息长度有界、严格字段校验、非法编码不会使服务端进程崩溃。断开后关闭该连接并重新接受新连接。
- 本地正常下注响应设计目标为 1 秒内；已在同机100盘记录耗时并核对，结果见testing.md；不推广为其他环境保证。
- 日志与终端区分用户提示和内部异常；服务端日志不得直接回传堆栈。stdout 用于交互，诊断可使用 stderr。

## 5. 交互流程及异常

连接 → welcome → round_open → 客户端输入 → bet → 服务端校验 → 实际掷骰/判型/结算 → round_result → 下一条 round_open → 再输入或 quit → bye → EOF。

空行仅在本地重新提示；其他非 quit 输入作为 command 字符串提交，由服务端裁决。客户端可以提示格式，但不得替代服务端验证。Ctrl-D/Ctrl-C 在连接可用时尽力发送 quit 并等待有限时间；异常断开仅清理资源，不保证 bye。

| 场景 | 预期行为 |
|---|---|
| 命令非法、非正整数、未知玩法/币种、下注超限 | error，可恢复，当前盘保持 OPEN |
| 余额不足 | 是否存在余额见 Q05/Q06；若将来启用账本则必须先验证、失败不扣款不掷骰，A1不启用该错误 |
| 客户端丢失连接 | 会话结束，服务端回到 accept；不自动重下注 |
| 服务端断开/请求后超时 | 客户端提示结果可能未知，结束本次会话；不得声称退款、不得自动重发 |
| 非法编码、超长帧、半帧后 EOF | 按协议关闭会话；不跨连接保留半帧 |
| 端口占用、连接拒绝 | 显示本机可读诊断，退出非零，不修改环境 |

## 6. 待确认登记表（唯一编号）

确认记录：用户在授权开发后明确选择“采用方案 A”，以下 Q01–Q09 全部按方案 A 冻结为 A1。保留原歧义和备选便于追踪，不再是实现阻断项。未来变更需同步规则、协议及测试预期。

| 编号 | 歧义 | 方案 A（已确认） | 备选及影响 |
|---|---|---|---|
| Q01 | 预叫产生方式和重复点数 | 每盘独立均匀抽两枚 1～6 骰子，保留顺序，允许相同；开盘后固定 | 人工预叫或禁止对子会改变分布和测试 |
| Q02 | 头彩、大彩同时中奖与结算 | 精确匹配时同时具备 tc/dc 资格；每盘只准一注，按所押玩法的赔率支付一次 | 只付 tc 会让押 dc 的玩家失去资格；叠加支付须新增多注规则 |
| Q03 | 普通点型优先级 | 最终点型按 tc→dc→kp→qx→dd→sx；tc 特例保留 dc 资格，其他低优先级均不获奖 | 独立判奖会改变多种重叠结果 |
| Q04 | 赔率是否含本金 | 一赔 N 表示净赢 N 倍，本金退回；未中净亏本金 | 若 N 为总返还，净赢变成 N−1 倍 |
| Q05 | 初始虚拟余额 | MVP 不设余额，只显示本盘输赢及币种，不显示虚构余额 | 若要余额，初值需用户指定，并扩充协议及账本测试 |
| Q06 | 三种币的关系 | 不兑换，金额始终带原币种；无账本时不维护三类余额 | 若启用账本则分别记账，汇率及初值不得猜测 |
| Q07 | 非法命令、断线、余额不足 | 非法输入不消耗盘；断线不恢复、不重发，结果丢失标记未知 | 恢复与余额持久化需要额外状态及协议 |
| Q08 | 每盘注数与限额 | 每盘仅一注，数量 1～1,000,000 整数，10 位以内纯 ASCII 数字再做范围校验 | 多注会影响 tc/dc 同时支付和事务边界 |
| Q09 | 连续游戏开盘时机 | 结果后立即新开盘，玩家下一次输入可下注或 quit | 增加 continue 请求需要协议及状态变更 |
