## 2. 每阶段任务和检查门

### 阶段0：本次停止点

1. 记录实际目录、OS、uv、Python和现有结构，禁止安装或修复环境。
2. 完成需求、架构、协议、规则、测试和计划；交叉核对接口、字段、时序及示例金额。
3. 输出待确认Q01–Q09及建议的影响，不选择性隐藏会影响实现的歧义。
4. 文档交付后停止，等待规则确认和明确的代码实现授权。这是业务冻结门，不是声称本次文档未完成。

### 阶段1：先建立业务真值

1. 将获确认的规则替换“方案A待确认”标记，冻结规则标识；若改余额/多注/赔付语义，先修订下游协议再写相应实现。
2. 从规则表列出确定性测试数据和金额边界，再实现 parse_bet、classify_roll、settle_bet。
3. 独立实现 generate_dice，生产使用标准库随机源；测试传固定抽样序列。
4. 交付物为一个纯业务模块及有意义的测试报告。没有网络也能验证全部判型与结算。

### 阶段2：先保证流边界

1. 实现协议消息结构的唯一验证位置，拒绝未知字段、非法类型/编码、重复键等。
2. 实现encode_message、decode_message、read_message、send_message，每连接独立缓冲与半帧时间。
3. 测试任意字节分割、中文拆分、多帧粘连、缓冲残留、极限长度及超时，不假设send/recv边界一致。
4. 交付可被两端直接调用的协议层，所有P用例通过后再接入服务端流程。

### 阶段3：串行服务端最小闭环

1. 配置回环host和port；定义同步accept及资源清理；同一时刻一活动会话。
2. 创建SessionState，发送welcome和round_open；校验请求编号与盘号。
3. 合法下注只抽一次实际骰子、只结算一次；发送结果后新开盘；业务错误保持当前盘。
4. 支持quit/bye、异常EOF、错误响应发送失败、Ctrl-C清理；传输失败不自动恢复或退款。
5. 先用协议级测试客户端做集成，避免真实客户端未完成阻碍服务端验证。

### 阶段4：终端客户端

1. 解析host位置参数和port选项，按协议顺序接收欢迎与开盘。
2. 输入下注或quit，将command原样封装；空行仅重提示，request_id单调递增。
3. 显示服务端实际点数的ASCII图及权威金额，明确原始匹配与最终资格的区别。
4. 业务错误重新提示；合法结果后读完下一盘才允许输入；响应关联失败立即关闭。
5. 覆盖Ctrl-D/Ctrl-C、连接失败和结果未知提示，避免自动重发。

### 阶段5：本机联调

1. 使用需求文档的显式本机解释器命令，确认uv不创建环境、不下载Python；若实际uv选项不兼容，记录并先修订命令，不安装升级。
2. 按testing.md运行标准库测试和两个终端E2E；网络测试仅发生于授权后的该阶段或其前置集成阶段。
3. 记录默认/自定义端口、100盘、断连、超时、重复请求、错误恢复和资源释放证据。
4. 失败回到对应模块修复并重跑受影响检查；规则变化先更新规则/协议/预期，不通过降低断言掩盖问题。

### 阶段6：最终验收

1. 根据testing.md逐项核实，不将未执行条目记为通过。
2. 完善README启动、停止、规则摘要、测试命令、已知限制和docs索引，保留原有重要内容。
3. 对照实际接口与消息重新审查Mermaid、错误码和请求响应配对。
4. 交付测试证据、未解决风险及范围声明；版本提交、推送和发布需另有授权。

## 3. 最小可运行版本及变更控制

最小版本只包含单客户端、每盘一注、单盘输赢、自动下一盘和正常退出。余额如被确认是必需需求，应先补初值、分币种账本与不足错误定义，再调整阶段1、3及测试，不可一边实现一边猜测。

任何核心规则变动应同步更新需求登记、规则真值、ruleset、协议金额说明、确定性用例和验收记录。技术接口变动同步两端与协议测试。数据库、账号、GUI、真实资金、第三方依赖、多桌或复杂并发都要独立评估，不属于本计划的默认授权范围。
